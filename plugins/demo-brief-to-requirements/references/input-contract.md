# DEMO-BRIEF-TO-REQUIREMENTS input contract

`briefPath` accepts either the original normalized shape (`briefing.id/owner/topics[]`, `acceptance`, `capacityAssumption`) or the actual scene 2/3 records: `{ memberId, briefing: { id, memberId, groups: [{title|summary, points?, scrapId|scrapIds}], scrapIds, todos? }, suggestion: {id, appId, change, evidenceScrapIds}, build: {status: "done", suggestionId, memberId}, capacityAssumption? }`. The adapter requires matching explicit member IDs on the briefing and build, maps only groups linked to the suggestion's evidence scrap IDs, and derives acceptance only from a successful same-suggestion build. Missing capacity becomes an explicit **scene 4 demo assumption of 100,000 concurrent users**, labeled as not an article claim. Failed, mismatched, or unproven records block conversion.

Output `requirements.txt` is exactly three lines: service, scale, and constraints plus the scene 4 draft rule to state assumptions and finish without questions. `requirements.json` preserves briefing/suggestion IDs, source IDs, assumptions and `assumptionSource`. The scene 4 TUI sends the model turn to an isolated scratch directory with no tool catalog; it restores the user's working directory afterward. The output graph then verifies the RFC, editable diagram, PNG and PDF. Explicit requests to ask questions stay in ordinary chat.
